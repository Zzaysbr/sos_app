# BLE peer association compatibility

Evidence requiring the addition: retained two-endpoint Chat/Location release tests and real iPhone → Android Chat rejection with five complete attempts using the same message ID. Account/Guest IDs cannot be compared with remote Bluetooth addresses/CoreBluetooth UUIDs, and neither platform exposes a portable self-address to solve this by substitution.

`peer.binding.v1` is an additive `BleMessage.type`, using the existing framed codec, checksum, 20-byte safe frames and service/RX/TX UUIDs. Its payload contains only a nonsecret installation ID, a 128-bit random nonce and optional `responseTo`. It carries no owner UID, auth token, SOS body or coordinates. A response must echo the challenge issued on that native peer's current ready connection. The receiver associates that peer with one installation ID for that connection; a different simultaneously connected peer cannot claim the same bound ID. The final response completes association when one side's initial hello arrived before the other's ready event. Hello attempts are bounded to three. Nonce-based freshness permits an immutable timestamp so overlapping retries keep identical bytes. Unbound Chat stays queued without consuming retry attempts or blocking SOS; explicit Location publication waits at most 40 seconds. Challenges, waiters, retry timers and bindings are cleared on retirement/disconnect; payload IDs/owners in existing queues are never silently converted.

Production startup obtains the same persisted installation ID across account changes. Android stores it in private SharedPreferences and iOS in UserDefaults; it is not a credential and is separate from `guest-local-device`. Reinstall/reset/backup restoration and native address changes may require explicit recipient selection. These IDs are not hardware-backed identities, certificates or encrypted authentication. A malicious device controlling the explicitly selected BLE connection can still lie about itself; this change prevents namespace confusion, unintended connected-peer routing and cross-peer replay, not radio-level impersonation or MITM.

New ↔ new: association gates Chat/Location; both endpoints still require correct incident route, sender, recipient and ACK/outbox source identity. ACK IDs/SOS/kind/destination checks remain. A replay of another incident does not establish permission. Location updates cannot establish their own incident route.

New ↔ old: unknown message type is ignored by the old coordinator. SOS without its optional sender ID retains the existing source-bound inbox/re-ACK path. New Chat/Location are withheld/rejected unless session association completes; the old account-ID payload is not treated as a native address. This intentional fail-closed compatibility limit needs UI/product communication before release. No fallback guesses the peer from proximity, login or a received replay. Existing old Chat with account-based sender ID and legacy SOS without an observed route remain preserved, with explicit recovery work still open.

Protocol framing/version, UUIDs, database schema and Firebase Rules did not change. No remote cloud identity/authorization is inferred from this exchange. Automated fake-radio results are separate from pending physical interoperability acceptance.
