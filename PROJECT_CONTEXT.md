## 1. Project Overview

`sos_app` เป็น Flutter application ชื่อใน UI ว่า **Emergency** สำหรับผู้ต้องการความช่วยเหลือ (`AppRole.needHelp`), ผู้ช่วยโดยสมัครใจ (`AppRole.rescue`) และผู้เปิดเครื่องเป็น relay รองรับ local-first SOS, nearby BLE, incident Chat และแผนที่ เป้าหมายคือคงการขอความช่วยเหลือเมื่อไม่มี Internet โดยเก็บข้อมูลลงเครื่องก่อน [Source: `lib/features/startup/presentation/startup_page.dart`, `lib/features/role/domain/app_role.dart`, `lib/features/sos/data/sos_repository.dart`]

ข้อจำกัดหลัก: BLE เป็น best-effort โดยมี Android connected-device foreground service และ iOS Bluetooth background modes สำหรับงานที่ได้รับอนุญาต แต่ยังไม่ผ่าน physical background acceptance (§ท้ายไฟล์); มี hop/time/retry limits; ต้องมีเพื่อนบ้านที่รองรับ protocol และ consent ที่เหมาะสม การบันทึกในเครื่อง, native write สำเร็จ, relay บันทึกสำเร็จ และผู้ช่วยปลายทางได้รับ เป็นคนละเหตุการณ์ ห้ามสื่อว่า SOS รับประกันถึงหน่วยกู้ภัยหรือเป็นบริการ dispatch ทางการ [Source: `SosBleCoordinator`, `HopRelayCoordinator`, `RelayProtocolLimits`, `RescueResponseBody` ใน `lib/features/nearby_ble/`]

## 4. System Architecture

### Initialization และ ownership

1. `main()` ใน `lib/main.dart`: ensure Flutter binding → `Firebase.initializeApp` → สร้าง `AppDatabase` → ขอ native `deviceIdentity` → โหลด locale → `runApp(SosApp)` หาก identity ว่างจะ throw; Firebase/identity ก่อน UI ยังเป็น dependency ของ startup แม้ SOS จะเป็น local-first
2. `SosApp` สร้าง `AuthService`, `LocaleController`, MaterialApp และ `StartupPage` ซึ่งเป็น animation 650 ms และเคารพ accessible navigation ไม่ใช่ตัว initialize BLE/network
3. `AuthGate._ensureResources` สร้าง owner-scoped `PersistentChatRepository`, `SosBleCoordinator`, `SosRepository`, `SosSyncCoordinator` ผู้ login ใช้ Firebase UID; guest ใช้ `guestDeviceOwnerId` (local namespace ไม่ใช่ authentication)
4. Cloud sync เริ่มเมื่อ authenticated; BLE เริ่มผ่าน `_startBleOnDemand` saved relay participation/pending relay อาจเรียกเริ่มเองจาก `SosPage._loadRelayPreference` จึงไม่ใช่ว่าทุก startup ต้องรอกดปุ่มเสมอ
5. เปลี่ยน account จะเพิ่ม resource generation, serialize BLE teardown และแทน `AuthSessionNavigator` เพื่อล้าง retained routes; `isSessionCurrent` ป้องกันงานของ session เก่าทำต่อ [Source: `lib/main.dart`, `auth_session_navigator.dart`, `sos_repository.dart`]

### Data flow

```text
SosPage → SosRepository → SQLite SOS + ordered SOS sync queue
                        → onSosCreated → Direct BLE outbox
                        → authenticated syncPending → SosCloudService → Firestore

SosPage + consent → SosBleCoordinator → HopRelayCoordinator
                  → signed RelayRepository jobs → native BLE → next peer

EmergencyChatPage → PersistentChatRepository → _enqueueChat (SosPage)
                  → verified incident participant → signed Chat relay
                  → otherwise applicable Direct Chat route (separate protocol)

native frame event → assembler → message-specific validation/authorization
                  → durable inbox/domain state → ACK/receipt ตาม protocol นั้น
```

Local database เป็นที่เก็บ working state; cloud queue กับ BLE queues แยกกัน ไม่มี distributed transaction ครอบคลุม local update + cloud + BLE ทั้งหมด `SosRepository.create` เก็บ SOS และ cloud command ใน transaction แต่ BLE enqueue เป็น callback ภายหลังและจับ error; coordinator มี reconciliation สำหรับ missing SOS outbox [Source: `SosRepository.create`, `BleDeliveryRepository.reconcileMissingSosOutbox`]

### Lifecycle

`SosBleCoordinator` poll ทุก 5 s เมื่อ OS อนุญาตและ observe lifecycle. `BlePresenceManager` ขอ optional `BleBackgroundExecution` ตาม aggregate radio leases: เริ่ม Android connected-device foreground service ขณะ UI foreground; คง leases/Hop processing เมื่อ background capability ได้รับอนุญาต มิฉะนั้น suspend แล้ว reconcile เมื่อกลับ foreground. Android `SosApplication` เก็บ FlutterEngine/bridge เดียวร่วมกับ Activity/service จึงไม่ dispose BLE เพียงเพราะ Activity ถูกทำลาย. iOS ประกาศ bluetooth-central/peripheral modes เพื่อรับ event-driven CoreBluetooth callbacks ขณะ background แต่ไม่มี state-restoration IDs/cold-launch headless bootstrap, ไม่มีการรับรอง continuous timers, OS-kill recovery หรือ force-quit. Active incident ที่มี owner-matched Help Offer คง Chat discovery/advertising แม้ send queue ว่าง/SOS transport TTL หมด โดยไม่เปิด participation ให้รับ SOS ผู้อื่น. Service หยุดเมื่อ radio leases สุดท้ายถูกปล่อย. ดูข้อจำกัด/validation ท้ายไฟล์; ทั้งหมดนี้ยังไม่ verified บนเครื่องจริง [Source: `sos_ble_coordinator.dart`, `ble_transport.dart`, `hop_relay_coordinator.dart`, `SosApplication.kt`, `BackgroundRuntime.kt`, manifest/Info.plist]

## 6. BLE Communication Architecture

### Transport, discovery และ connection

| ขั้นตอน | ผู้รับผิดชอบ | พฤติกรรมที่พบ |
|---|---|---|
| Native channel | `BleTransport` ใน `lib/features/nearby_ble/data/ble_transport.dart` | methods `sos_ble_transport/methods`, events `sos_ble_transport/events`; cache connection snapshots แยก peer/role |
| Advertising/scanning | `BlePresenceManager.acquireDiscovery/acquireAdvertising`, `_reconcile` | shared instance ต่อ transport, leases รวมความต้องการแต่ละ feature, serialized start/stop; ไม่ start ใหม่ทุก poll ถ้ายัง active |
| Android | `BleTransportBridge` ใน `android/app/src/main/kotlin/com/n1cxltine/sosapp/BleTransportBridge.kt` | BLE GATT server/client; service-filtered scan, scan session, write/notification queues, permission/adapter checks; connection/setup timeout 15 s, write callback timeout 5 s |
| iOS | `BleTransport` ใน `ios/Runner/BleTransport.swift` | CoreBluetooth central/peripheral; discovery, service/characteristic discovery, TX subscribe, queued peripheral notifications และ backpressure |
| Native registration | `MainActivity` / `AppDelegate` ใน native app directories | register custom transport/preferences; native device identity แยกจาก signing key |
| Peer connection | `SosBleCoordinator._onEvent`, `HopRelayCoordinator.onEvent/_maybeConnect` | central/peripheral แยก role; native connected หลัง notification readiness; connected ไม่เท่ากับ authenticated |
| Authentication | direct `_beginPeerBinding/_handlePeerBinding`; relay capabilities + session challenge/response | Direct binding เป็น incident routing aid; Relay ต้องพิสูจน์ Ed25519 key/session ก่อนส่งข้อมูลตาม gates |

Native service/RX/TX UUIDs อยู่ในทั้งสอง bridge ต้องคงให้ตรงกัน Protocol นี้ไม่ได้ใช้ vendored Nearby package เป็น production radio path OS permissions และ saved relay consent เป็นคนละชั้น

### Encoding, fragmentation และ reassembly

`BleMessageCodec` ใน `ble_protocol.dart`: outer JSON version 1 มี `id`, `type`, `createdAt`, `payload`, CRC32; maximum encoded message 64 KiB ค่า default frame 20 bytes, header 14 bytes เหลือ payload **6 bytes/frame** เพื่อใช้กับ ATT MTU ต่ำสุด CRC32 ตรวจ accidental corruption เท่านั้น ไม่ใช่ authentication

`BleMessageAssembler.accept` รองรับ out-of-order frames, conflicting duplicate detection และ incomplete timeout 10 s; delivered ID cache default 1,024 การ expire เกิดเมื่อรับ input ครั้งถัดไป Coordinator สามารถปิด transport-level duplicate suppression เพื่อ re-ACK จาก durable state มี assembler แยกตามเส้นทางรับใน coordinator ต้องไม่แชร์ incomplete state ข้าม peer/role

`BleMessageWriteQueue.sharedFor(...).sendFrames` serialize งานต่อ peer และยก control messages ก่อนงานอื่นระหว่าง frame writes ทุกชั้นต้องแยก native write completion ออกจาก application receipt

### Routing, persistence, retry และ recovery

- **Direct v1:** `BleDeliveryRepository` เก็บ `bleOutbox/bleInbox`, stable message ID, state transitions, claim/recovery, peer/incident matching และ reply destination; `SosBleCoordinator` ใช้ ACK handlers แยก SOS, Chat และ Location retry default 2 s base, cap 5 min, maximum 8 attempts, stale recovery 30 s [Source: constructors, `_drain`, `_markFailed`, `recordAcknowledgement`, `recordLocationAcknowledgement`]
- **SOS Relay v2:** `RelayRepository.persistOriginOffer/acceptIncomingOffer/createNextHopAttempt/prepareOutgoingOffer/persistReceipt` เก็บ origin, attempts, receipts; ตรวจ signature/digest/path/session และ quota; deterministic attempt ID ใช้ correlation; แยก `hop` กับ `finalRecipient` receipt ใน `RelayReceiptType`
- `RelayProtocolLimits`: maximum lifetime 30 min, 3 hops, path entries 4, 50 jobs, logical payload storage 1 MiB, emergency text 512 bytes, clock skew 2 min, maximum attempts/message 5; `RelayRepository.maximumRetriesPerPeer` = 3 ข้อจำกัดนี้ไม่ใช่ Chat retry budget และไม่ใช่ SQLite physical file size limit [Source: `domain/relay_envelope.dart`, `data/relay_repository.dart`, `relay_storage_accounting.dart`]
- **Chat relay:** `ChatRelayRepository` owner-scoped inbox/outbox; immutable envelope + received signed path สำหรับ forwarding; `due` คัด expiry/retry; maximum 8 attempts ทั้ง write สำเร็จและ fail, backoff 5→10→20→40→80→160→320 s, signed lifetime ไม่เกิน 30 min [Source: `chat_relay_repository.dart`, `ChatRelayBody.validate`]
- `HopRelayCoordinator._processChatRelayDue` เลือก final recipient ที่ authenticated ก่อน มิฉะนั้นเลือก participating peer ที่ไม่อยู่ใน path; ไม่ใช่ global shortest-path routing; ตรวจ session/participation ซ้ำก่อนแต่ละ send ผ่าน `sendAllowed`
- Session Proof มี nonce, roles, generations, signed challenge/response, timeout/recovery; established proof ไม่มี time-based lease ต้อง invalidate เมื่อ session เปลี่ยน [Source: `_RelaySession`, `_issueSessionChallenge`, `_handleSessionResponse`, `_retryFailedSessionProofs`]
- Chat authorization evidence แยกจาก SOS transport lifetime: `RelayRepository.cleanupExpired` เก็บ signed origin ที่ตรวจ integrity แล้วไว้ขณะยังมี unexpired/nonterminal Chat outbox อ้างอิง หรือ active local incident พร้อม response record ของ owner เดียวกัน ไม่แก้ signed expiry/retention deadline และ `listForwardableMessages` กรองทั้งสองเวลาอย่างชัดเจน จึงส่ง SOS ที่หมดอายุซ้ำไม่ได้ หลักฐานยังนับใน quota 50 records/1 MiB เดิม และล้างได้เมื่อ transport หมดอายุพร้อมไม่มี live Chat reference เหลือ [Source: `_hasChatReference`, `test/chat_origin_retention_test.dart`; host-verified ยังไม่ retest บนเครื่องจริงของ fix นี้]
- `processDue`, `_drainChatArrivals`, `_chatArrivedDuringDrain` coalesce งานและให้ Chat ที่เข้าระหว่าง drain ได้รอบถัดไปทันที; stop/dispose ยกเลิก listeners/timers/presence [Source: coordinator ทั้งสอง, `test/stage2_chat_runtime_test.dart`]

## 7. SOS Communication Lifecycle

### เป้าหมาย A (victim) → B (relay) → C (rescuer)

1. `SosPage._sendSos` ตรวจ active own incident, เก็บ SOS ไม่มีพิกัดก่อน แล้วเริ่ม `_beginAutomaticEmergencyRouting` แบบ asynchronous และเปิด incident Chat
2. Consent แยก `allowPublicRelay`, `allowVoluntaryRescue`, `shareLocation` และการให้เครื่องตนช่วย relay คนอื่น ค่า `EmergencyConsent.safeDefault` ปิดทั้งหมด การให้ C เห็น rescue candidate ต้องใช้ voluntary-rescue scope ไม่ใช่ public relay อย่างเดียว [Source: `emergency_consent_store.dart`, `SosPage._beginAutomaticEmergencyRouting`, `HopRelayCoordinator.queuePublicEmergency`]
3. A สร้าง immutable signed SOS; B ตรวจ trusted immediate session + offer, persist ก่อน hop receipt และสร้าง forwarding attempt; C ตรวจซ้ำและ `RescueInboxRepository` บันทึก candidate เมื่อ mode/scope เหมาะสม [Source: `_handleIncomingOffer`, `RelayRepository.acceptIncomingOffer`, `rescue_inbox_repository.dart`]
4. C ต้องส่ง signed Help Offer ที่ผูก origin/digest; reverse response jobs ใช้ preceding SOS path กลับ C→B→A และมี `rescue.offer_ack` [Source: `_handleIncomingRescueTransfer`, `_processRescueResponseDue`, `rescue_response_repository.dart`, `rescue_response_envelope.dart`]
5. Chat ของ A↔C ส่งผ่าน B ได้เมื่อมี verified SOS + explicit signed Help Offer และ signed transfer path ปลายทางเก็บ Chat ใน local owner scope; intermediary เก็บ relay inbox/outbox [Source: `ChatRelayAuthorization.authorize`, `_handleIncomingChatRelay`, `SosBleCoordinator._persistRelayedChat`]

| Message | ปัจจุบัน / Evidence | ข้อจำกัดที่ต้องรักษา |
|---|---|---|

## 8. Security Architecture

### Identity และ trust boundaries

| Identity / boundary | ความหมาย / Source |
|---|---|
| Firebase UID | authenticated owner ของ cloud/local account data; `AuthService`, `SosRepository`, Firestore rules |
| Guest owner namespace | local device history scope; ไม่ใช่ cloud user/ไม่ migrate เป็น account อัตโนมัติ; `guestDeviceOwnerId`, guest continuity tests |
| Native `deviceIdentity` / BLE address | installation/routing reference แยกจาก cryptographic key; native bridges และ direct peer-binding handlers |
| Relay installation key | Ed25519 public-key-derived key ID; `RelayIdentityService`, `RelayCryptography.publicKeyId` |
| Immediate peer vs original sender | Session Proof พิสูจน์ adjacent key; origin signature + incident authorization พิสูจน์ payload/สิทธิ์อีกชั้น |
| Voluntary rescuer | ต้องมี signed offer ที่ผูก incident; ไม่พบ credential authority/verified professional responder integration ในเส้นทางนี้ |

`PlatformRelayPrivateKeyStore` ตั้ง Android Keystore-wrapped storage และ iOS local non-synchronizing `unlocked_this_device` Keychain; `RelayIdentityService.loadOrCreate` serialize initialization, persist/read-back seed และ fail closed เมื่ออ่าน/เขียนไม่ได้ Direct v1 ไม่ควรถูกยกระดับให้มีความปลอดภัยเท่า Relay v2 เพียงเพราะใช้ radio เดียวกัน [Source: `lib/features/nearby_ble/data/relay_key_store.dart`]

### Validation ที่ต้องทำร่วมกัน

- ตรวจ canonical body/signature, key-ID↔public-key mapping, immutable digest, expiry/clock skew, path/hop bound และ session freshness [Source: `RelayCryptography`, envelope validators, `HopRelayCoordinator`]
- Chat: self-consistent signer อย่างเดียวไม่พอ `ChatRelayAuthorization.origin/authorize` ตรวจ stored signed voluntary-rescue SOS + digest และ explicit signed rescuer offer; sender/recipient ต้องเป็น victim/rescuer คู่นี้ พร้อม timestamp ordering รองรับ legacy incident-ID binding โดยยังต้องตรวจ origin/offer เหมือนเดิม
- Chat signed hop chain ผูก previous chain, immutable envelope, offer, max hops และ next hop; reject missing/tampered/truncated/loop path; หลัง await verification ตรวจ active session ซ้ำ [Source: `ChatRelayTransfer.verifyPath/forNextHop`, `_handleIncomingChatRelay`, `test/stage2_chat_security_test.dart`]
- Lifecycle: signature ถูกต้องแต่ key ไม่ตรง trusted incident origin ยัง reject; unknown origin ต้อง defer และ reconcile เมื่อ genuine SOS มาถึง; event ID เดิมแต่ payload ต่างต้อง reject [Source: `IncidentLifecycleRepository`, `test/incident_lifecycle_authorization_test.dart`]
- Replay/dedup: stable message/event/attempt IDs และ durable inbox checks, proof nonce/session bindings; ไม่มี global guarantee of exactly-once delivery; receiver idempotence ต่างจาก transport ส่งครั้งเดียว
- Ownership: queries/session guards และ Firestore rules ตรวจ account owner; rescue materialization ใช้ `deviceOnly`, ไม่ upload เหตุของคนอื่น [Source: `SosRepository.ensureReceivedIncident`, `PersistentChatRepository._requireAuthorizedSos`, `AuthGate`, `security-tests/firestore.rules`]

**Confidentiality:** signed text/relay payload เป็น plaintext; ไม่พบ end-to-end encryption ใน implementation ปัจจุบัน CRC ไม่ป้องกัน malicious forgery และ Direct peer-binding ไม่ใช่ Ed25519 identity proof ห้ามยึด comment ที่เรียก outer envelope ว่า “authenticates” มาอ้างว่ามี cryptographic authentication ทุก message type [Source: `BleMessageCodec`, `LocationBleEnvelope`, `SosBleEnvelope`, `RelayCryptography`]

Firestore rules ถูกกำหนดใน `firebase.json` ให้ใช้ `security-tests/firestore.rules`: signed-in owner only, exact SOS field set, create active, createdAt คงเดิมเมื่อ update Rules ชุดนี้ไม่ได้ทำ origin-signature verification หรือรับประกัน terminal monotonicity เหมือน BLE lifecycle; การมี rules file ไม่ยืนยันว่า deployed project ใช้ version นี้อยู่

### Password Recovery: พฤติกรรมจริงกับ design เดิม

`AuthService.resetPassword` ปัจจุบันเรียก `FirebaseAuth.sendPasswordResetEmail`; หน้า Forgot Password (`lib/features/auth/presentation/auth_page.dart`) และ Account (`lib/features/sos/presentation/account_page.dart`) เรียกบริการนี้ มี neutral response สำหรับ user-not-found และ tests ที่ตรวจการส่ง email reset (`test/password_recovery_test.dart`) จึงห้ามนำรายงานเก่าที่บอกว่า email reset ถูกปิดมาใช้เป็น current status นี่เป็น email-based reset **ไม่ใช่ genuine MFA recovery**

อีกเส้นทางหนึ่งคือ `PasswordRecoveryCoordinator` ใน `lib/features/auth/data/password_recovery.dart`: transaction TTL default 10 min, maxAttempts 5, แยก email/secondFactor proof, ตรวจ transaction/account binding และ one-time completion แต่ backend default `UnavailablePasswordRecoveryBackend` ไม่ทำงานจริง และไม่ใช่เส้นทาง reset ที่ UI ใช้อยู่ การมี class นี้ไม่ทำให้ email reset ปัจจุบันมี second factor ไม่มี trusted recovery backend deployment ใน repository; หาก product ยังต้องการ genuine MFA ต้องตัดสิน requirement ให้ชัด และ implement/test trusted backend ที่ผูกสอง proofs กับ UID/transaction โดย enforce expiry/replay/rate-limit/change-password แบบ atomic โดยไม่เก็บ credential ใน client

### การตัดสินใจด้าน Trusted Responder ที่ต้องรักษา

Historical owner decision **TRD-001 (2 พฤศจิกายน 2026): Option A — Safe Minimal MVP** อนุมัติเฉพาะขอบเขต Direct v1 + truthful hop-only Relay v2; **Final Delivery v3 ถูก deferred** ไม่ได้อนุมัติให้สร้าง authority/credential/backend ใหม่ voluntary-rescue SOS/Help Offer ปัจจุบันเป็น peer assistance แยกจาก professional Trusted Responder v3 การมี final receipt model ไม่แปลว่ามี authorized production responder หรือ human acceptance

ตารางนี้ย่อ decision register เดิมที่สำรองไว้ (§17); คำว่า Proposed/Deferred/Blocked เป็น historical decision state ไม่ใช่การอนุมัติใหม่:

| Decision | สาระที่ต้องรักษา / สิ่งที่ยังขาด |
|---|---|
| TRD-002–004 | Production trust root/eligibility/enrollment ต้องมีผู้รับผิดชอบจริง; pilot ต้อง labelled test และ enrollment ตรวจสอบได้; ห้าม self-registration ให้สิทธิ์ responder |
| TRD-005–006 | Credential expiry/status freshness/revocation policy ยัง Proposed; offline ตรวจได้เฉพาะ signed evidence ที่มี ไม่ทราบ revocation ใหม่ทันที |

ก่อน v3 ต้อง freeze canonical wire/route-evidence schema, deterministic receipt/persistence IDs, atomic incident+dedup+receipt+reverse-route commit ก่อนส่ง, restart/conflict tests และ controlled-pilot prerequisites การเสนอ final **Chat** receipt ใน §13 ไม่ใช่การอนุมัติ professional Trusted Responder v3 [Historical decision provenance: archived Trusted Responder decision/design/review/roadmap documents ใน §17; current source: `relay_envelope.dart`, `hop_relay_coordinator.dart`, `relay_key_store.dart`]

### คู่มือทดสอบเครื่องจริงที่รวมแล้ว (ยังไม่ใช่ผลการรัน)

ก่อนเริ่ม: ใช้ synthetic incidents/test accounts และ build ที่ระบุ source SHA + working-tree digest, version/mode, artifact SHA-256, OS/model, direction, foreground/lock state, permissions และ topology ใช้ aliases แทน serial/UDID/account identifiers ห้าม uninstall/clear data/reset pairing เพื่อแก้ปัญหา signing หรือ connectivity; package ID ใหม่เป็นคนละ sandbox ไม่ใช่ update-in-place ที่รับรองประวัติเดิม

ทุก case ต้องมี **ID, วัตถุประสงค์, preconditions, numbered actions, expected result, actual observations, sanitized evidence และ PASS/FAIL/PARTIAL/NOT RUN/BLOCKED** PASS ต้องครบทุก expected observation; ขาด evidence ไม่ใช่ PASS เก็บ raw private logs นอก source control ขั้นตอนต่อไปนี้เป็นสิ่งที่ต้องทำใน session ที่ได้รับอนุญาต ไม่ใช่สิ่งที่งานรวมเอกสารได้ทำแล้ว

1. **State/role baseline:** เตรียม active own SOS และ pending test message; สลับ needHelp→rescue→banner กลับเหตุเดิม ตรวจ incident/message/destination/queue state ไม่เปลี่ยน ทำซ้ำหลัง process restart; Rescue mode ไม่ใช่สิทธิ์ครอบครองเหตุ
2. **Direct BLE matrix:** Android↔iOS และ Android↔Android แยกแต่ละทิศทาง; discovery→GATT ready→bound peer→SOS/Chat/Location; correlate enqueue, write, receiver persist, ACK และ sender acknowledged; ตรวจหนึ่ง receiver row ต่อ logical ID อย่าใช้ขั้นตอนนี้อ้าง final multi-hop Chat receipt
3. **Pending/restart/dedup:** ทำ receiver unavailable→queue→ปิด sender→เปิดใหม่→reconnect; message ID/owner/incident คงเดิม, bounded retry, duplicate persist idempotent และ re-ACK ตามชนิด message; stale callback ของ connection เก่าต้องไม่ retire session ใหม่
4. **Multi-hop:** บังคับ A↔C ติดต่อไม่ได้; A victim/B relay/C rescuer พร้อม consent/scope; ตรวจ SOS persisted ที่ B/C, signed Help Offer กลับ A, A↔C Chat ผ่าน B รวม repeated conversation, loss/reconnect/restart และ cancel/resolve origin authorization; แยก forwarded, hop receipt และ final receipt ที่ยังขาด
5. **Controlled fault cases:** ACK-loss ต้อง suppress หลัง durable persist ก่อน encode/send ด้วย lab harness แบบ one-shot ที่ผูก exact ID/kind/peer/expiry และ auto-disarm; ไม่แทนด้วย Bluetooth off Wrong-peer ACK ต้องมาจาก third native connection จริง ค่า default/release ต้องไม่เปิด suppress/spoof ได้ หากไม่มี harness ที่ตรวจแล้วให้ NOT RUN ห้ามเพิ่ม production bypass เพื่อให้ case ผ่าน
6. **Permissions/lifecycle:** revoke/regrant Bluetooth และ When In Use location, adapter off/on, background/resume, explicit reconnect; ไม่มี false Connected/Delivered/fabricated fix; SOS/history ไม่หาย; บันทึกว่าจำเป็นต้อง restart หรือไม่ Restore permissions/network หลังจบ
7. **Q-806 identity/sync:** Guest create offline→restart→login A→logout→B→กลับ A; Guest อยู่ device history ไม่ auto-merge/upload, A/B data ไม่รั่ว, retained routes/streams ถูกล้าง; ทดสอบ pending A sync แล้วเปลี่ยน B ก่อน restore network และตรวจ original owner/หนึ่ง cloud document ผ่าน authorized synthetic environment แยก UI filtering จาก deployed rules
8. **Map/GPS/offline:** เปิดเหตุที่มี stored coordinates→pan/zoom/recenter→leave/reopen; network off→unseen area→restore→retry→second unseen area เพื่อแยก fresh fetch จาก cache; attribution อ่านได้และ links ถูก host; deny GPS ไม่ล้าง incident marker; large OS text ไม่บัง controls สำหรับ Offline Region ต้อง download complete→restart→network off→ตรวจ real tiles ตาม bounds/zoom และ outside-region unavailable; รวม cancel/interrupted download/low storage
9. **Q-803 accessibility:** TalkBack และ VoiceOver แยกเครื่อง/ผล; ใช้ existing synthetic incident และไม่ส่งข้อความเพื่อทดสอบ focus; SOS ประกาศ label/button/enabled/hold hint ถูก, History→Chat→Details→Back focus สมเหตุผล, text/send/consent/stop/dialog controls มีชื่อไม่มี focus trap; ตรวจ large text/light/dark/reduced motion ไม่ใช้สีอย่างเดียวและคืน OS settings
10. **Range/quality:** safe field site, 5/10/20/30/50 m ที่ทำได้, open+obstructed, ≥3 runs × ≥30 s ต่อ condition; บันทึก orientation/height/obstruction/OS และแยก run เมื่อ reconnect; `attempted = acknowledged + nativeFailed + timedOut + pending`, ACK latency min/avg/p50/p95/max และ PDR; RSSI เป็น scan-time signal ไม่ใช่ระยะหรือ range guarantee [Source: `lib/features/nearby_ble/domain/ble_range_diagnostic.dart`, `test/ble_range_diagnostic_test.dart`]
11. **Cleanup:** ปิด sharing/scan/advertising/harness/injector, restore account/network/permissions ที่ตกลงไว้, เปิด histories ตรวจ counts/ownership และบันทึก pending jobs; เมื่อ recovery fail เก็บ logs แล้วหยุด session ห้ามล้างข้อมูลเพื่อซ่อนผล

Rules emulator reproduction (ยังไม่ได้รันในการรวมเอกสาร): ตรวจ Java/Firebase CLI และ port 8080 ว่างก่อน ไม่ kill service อื่น; dependencies ต้องพร้อม แล้วใช้:


### Design Context ที่รวมจาก CLAUDE / Impeccable

ผู้ใช้อาจเครียด ใช้มือเดียว อยู่กลางแจ้งและมีเวลาอ่านน้อย บุคลิก UI ต้องสงบ เด็ดขาด น่าเชื่อถือ และบอกข้อจำกัดตามจริง Need Help ใช้สีแดงเฉพาะเหตุฉุกเฉิน/การขอช่วย; Rescue ใช้เขียวเข้ม/น้ำเงิน แต่ต้องแยก mode ด้วยคำ ไอคอน hierarchy และ navigation ร่วมกัน ไม่พึ่งสีอย่างเดียว ทั้ง light/dark ต้องรักษาคอนทราสต์ อ่านกลางแจ้งได้ และ touch target อย่างน้อย 48 logical pixels

ให้ urgent action มาก่อนรายละเอียด ป้องกัน duplicate taps, คง incident/delivery เมื่อสลับ mode พร้อมทางกลับ active SOS และอธิบาย empty/offline/error/stale/permission states พร้อมทางทำต่อ หลีกเลี่ยง game styling, glow, glassmorphism, nested decorative cards และ animation รบกวนเหตุเร่งด่วน ใช้ motion เพื่ออธิบาย state change พร้อมเคารพ reduced motion นี่เป็น **design requirements** ที่เก็บจาก config เดิม ไม่ใช่การรับรองว่าทุกหน้าผ่านแล้ว

## 13. Development Priorities

ลำดับต่อไปนี้เป็นข้อเสนอจาก gaps ที่ตรวจพบ ไม่ใช่สถานะว่าเริ่มทำแล้ว:

1. **Core communication correctness:** tagged stale-disconnect guard และ deterministic default tests ผ่านแล้ว (§11); ถัดไปกำหนด/implement signed final Chat receipt และตรวจ native callback บนเครื่องจริง โดยคง baseline นี้
2. **Multi-hop reliability:** repeat A-B-C radio acceptance, durable retry/reconnect/duplicate/receipt correlation; รักษา existing Session Proof และ signed hop checks
3. **Bidirectional SOS lifecycle:** ทดสอบ SOS→Help Offer→Chat→cancel/resolve ทั้ง topology, loss/restart/deferred origin; ปิด local terminal vs failed enqueue gap และกำหนดอำนาจ resolve ของ rescuer
4. **Security/data integrity:** origin/participant ownership consistency ข้าม direct/relay/cloud, terminal transition rules, replay/trust invalidation และ key-loss/reinstall policy โดยไม่ผ่อน validators
5. **Performance/resources:** วัดจริงก่อนปรับ polling; bounded queues/assembler/inbox cleanup, incremental reassembly และ logging budget; แยก latency/CPU/energy evidence
6. **Chat/media/location completeness:** final receipts ก่อน delivered UX; media signed manifest/resumable transfer/quota; ออกแบบ multi-hop location ต่างหากจาก initial snapshot
7. **UX/UI:** ลด SOS→Chat blocking path, เก็บ localization ที่ตกหล่น, เพิ่ม font/theme controls ตาม product decision และ physical accessibility tests
8. **Final regression/device acceptance:** host suite + explicit contracts + emulator rules + native builds + repeat device matrix พร้อม sanitized evidence/source digests ก่อนอ้าง release readiness

### Build / Demo Gate / Store Distribution Gate

App identity ปัจจุบัน Android namespace/application ID และ iOS Runner bundle ID คือ `com.n1cxltine.sosapp` (`android/app/build.gradle.kts`, `ios/Runner.xcodeproj/project.pbxproj`) รายงานเก่าที่ใช้ Android `com.example.sos_app` เป็นประวัติก่อน migration; อย่าทำ migration ซ้ำจาก roadmap เก่า ID เปลี่ยนหมายถึงคนละ sandbox ต้องมี explicit data-continuity plan และ Firebase/store/provider registrations ที่ตรงกัน

Demo ใช้ Android Debug หรือ iOS Development/Profile ที่ลงและเปิดบนเครื่องจริงได้ ส่วน Store Distribution ต้องมี owner-controlled Android upload signing + inspected AAB และ Apple Distribution/profile + archive/export; debug/development/no-codesign build ไม่ผ่าน Store Gate Android release config fail closed เมื่อ signing properties ไม่ครบ (`android/app/build.gradle.kts`) iOS Runner Release ขอ Apple Distribution แต่ config ไม่ยืนยันว่ามี certificate/profile ใช้งานได้แล้ว (`ios/Runner.xcodeproj/project.pbxproj`) งานเอกสารนี้ไม่ได้ตรวจ credentials/Console/build ใหม่

ตัวอย่าง build สำหรับ session ที่ได้รับอนุญาต: map define file เป็น private local JSON ที่ไม่ commit/print; ใช้ placeholder path แทนค่าจริง:

```sh
flutter build apk --debug --no-pub --dart-define-from-file=/private/path/map.release.json
flutter build ios --debug --no-pub --dart-define-from-file=/private/path/map.release.json
```

Install ให้ใช้ update-in-place ของ identity/signature เดิมและตรวจ Guest/history หลัง Home Screen launch; signing mismatch ให้หยุด ไม่แก้ด้วย uninstall สำหรับ release ต้องตรวจ app ID/version, artifact/signing fingerprints, permissions/entitlements, provider attribution และ source digest จาก artifact จริง แผนที่ใช้ `GEOAPIFY_API_KEY` หรือ explicit `MAP_TILE_URL`/`MAP_TILE_ATTRIBUTION`/`MAP_TILE_USER_AGENT` ตาม `MapTileProviderConfig` ไม่คัดลอกคีย์ลงเอกสารและไม่ยึดราคา/terms เก่าเป็นข้อเท็จจริงปัจจุบัน

Store Gate ยังไม่มี evidence ปิดครบ: signed Android/iOS distribution, current-build physical reliability/negative paths, provider account/quota/terms และ live auth/rules/isolation ต้องตรวจแยกกัน genuine MFA backend เป็น requirement ที่ยังต้องยืนยันตาม §8 ไม่ใช่สิ่งที่ email reset ปัจจุบันทำสำเร็จแล้ว

### Future LoRa — ยังไม่ใช่งาน implementation

LoRa เป็นแนวทาง hardware-backed experiment ที่ deferred และไม่มี app transport implementation ปัจจุบัน `BleTransportClient` ยังผูก discovery/connection roles กับ BLE; อย่าเปลี่ยนเป็น generic radio abstraction จน accessory+firmware protocol ที่เลือกพิสูจน์ boundary ได้ ต้องกำหนด provisioning/authenticated encryption/replay, payload/airtime/fragment/window/retry budgets, durable application ACK, coexistence, key recovery และ field matrix แยกใหม่ Image/video และ high-frequency location ไม่ถือว่าใช้ได้บน radio นี้โดยอัตโนมัติ

ก่อนจัดซื้อ/ทดลองส่งต้องตรวจ hardware, phone-to-accessory compatibility, certification/กฎวิทยุปัจจุบัน และ throughput/energy จริง ไม่ย้ายราคา ช่วงความถี่ หรือ compliance claim จาก feasibility report เก่ามาเป็นข้อมูลล่าสุด Scope/proposal เดิมมีใน backup (§17); ไม่มี dependency/adapter/firmware ถูกเพิ่มจากการรวมเอกสาร

## 15. AI Development Guidelines

1. Read `PROJECT_CONTEXT.md` before making changes. ตรวจ working-tree status และอ่าน source/config/tests ที่เกี่ยวข้องก่อน implement; จดว่ามี uncommitted work ใดอยู่แล้ว ห้าม overwrite โดยพลการ
2. Preserve existing working functionality. เปลี่ยนแบบ incremental/testable; ไม่ rewrite subsystem ใหญ่จากคำบอกเล่าหรือ speculative performance issue
3. Analyze downstream impacts before changing shared protocols. ตรวจ Dart/native ทั้งสอง platform, stored envelope compatibility, schema migration, old peers, ACK/retry/UI semantics และ security boundaries
4. คง stable incident/message IDs, original sender/final recipient, owner scope, immutable signatures และ session checks แยก hop storage กับ final delivery เสมอ
5. Add regression tests for bug fixes; ใช้ deterministic clock/fake radio เฉพาะ boundary ที่จำลอง และอย่าอ้างผลจำลองเป็น device verification
6. Never weaken security validation to make tests pass. อย่าข้าม signature, ownership, participant proof, TTL, session หรือ replay checks; แก้ expired fixture ที่ clock/fixture
7. รัน focused checks ที่ตรงกับ change แล้ว full relevant suite; explicit `regression/` ต้องรายงานแยก default tests; ไม่ซ่อน failing tests ด้วย skip/delete หรืออ้างทั้ง suite PASS เมื่อมี failure
8. ห้าม log/export seed, token, API key, user content, exact coordinates หรือ private device/user identifiers; ตัวอย่างให้ใช้ test-only synthetic values เก็บ sanitized source digests/result artifacts หากเป็น acceptance
9. Update `PROJECT_CONTEXT.md` เมื่อ architecture, protocol, requirements หรือ implementation status เปลี่ยน พร้อม date, source/test references และ evidence scope
10. Never mark a feature as verified without supporting evidence. บันทึก command/result/build/source scope แยก Implemented, Verified by Tests, Not Verified on Devices, Planned และ Broken; ไม่ใช้ old report แทน current validation

Audit พบ shared frame queue ไม่มี Dart write deadline, lifecycle ระงับ BLE เมื่อ background, ไม่มี Android foreground service/iOS Bluetooth background modes และ notification page เดิมเป็น mock. แก้ source แล้วตามขอบเขตด้านล่าง แต่ไม่ใช่ verified background behavior; ไม่รับประกัน iOS always-on/force-quit recovery หรือ delivery เมื่อวิทยุ/permissions ไม่พร้อม. System notification ต้องเกิดหลัง authorized incoming Chat durable persistence เท่านั้น ไม่ใช่ intermediate relay และไม่แก้ final Chat receipt contract ที่ยังล้มเหลว.


Implementation scope รอบ background/notifications:

- `BleMessageWriteQueue`: default 10 s/frame watchdog; abort queued work ของ peer เดียวกันและ bounded disconnect เมื่อ native callback หาย ไม่ส่ง tail ของ logical message เก่าหลัง completion มาช้า. `BleTransport._call` bounded operation deadlines (ordinary 8 s, initialize/advertise 20 s, permission 2 min) เพื่อไม่ให้ active-call counter pin disposal; ไม่ถือ local write เป็น application ACK.
- `HopRelayCoordinator`: native adapter unavailable ล้าง ephemeral proof/session maps; reconnect budget เดิม 2 ครั้ง/peer เปิดใหม่หลัง cooldown 30 s โดยยังคง maximum candidate identities เดิม. Active local incident + owner-matched response คง discovery/advertising เพื่อรับ Chat หลัง queue ว่าง/transport TTL; terminal incident ปล่อย Chat presence หากไม่ participating/pending. ไม่มี schema/wire/proof validation/TTL change.
- `BleBackgroundExecution` optional interface และ production platform channel เชื่อม aggregate presence กับ native execution. Transport จำลองที่ไม่มี capability ยัง suspend ตามเดิมเมื่อ background. OS refusal ไม่สื่อว่า background เปิดสำเร็จ.
- Android `SosApplication.kt` เป็นเจ้าของ retained engine/bridge; `MainActivity` attach/detach permission activity และไม่ dispose shared radio เมื่อ destroy. `BleBackgroundService` connectedDevice/START_NOT_STICKY พร้อม ongoing activity notification, ไม่มี boot receiver/auto restart หลัง kill. เพิ่ม required foreground-service/Bluetooth/notification permissions, permission notification แยกจาก Bluetooth และไม่ block SOS เมื่อปฏิเสธ; retry request เมื่อ resumed กรณี permission dialog เดิมยังบังอยู่ แต่ไม่ auto-prompt ซ้ำหลัง Android denial. Android adapter broadcast retire native GATT บน power off, emit canonical poweredOn เพื่อ reconcile saved leases; stopAdvertising callback เป็น null-safe.
- iOS `UIBackgroundModes` bluetooth-central/peripheral อนุญาตงานตาม Bluetooth events; native disconnect/power-loss ยกเลิก pending sends/readiness. ยังใช้ implicit Flutter engine เดิม ไม่มี CoreBluetooth state restoration/headless cold relaunch. BLE background advertising ของ iOS มีข้อจำกัดการค้นหาข้ามแพลตฟอร์ม จึงต้องทดสอบ iOS central→Android advertised service โดยเฉพาะ ไม่รับรอง OS suspension/process termination/force-quit.
- `ChatNotifications` + `PersistentChatRepository.onIncomingPersisted`: callback หลัง authorized incoming DB commit, owner/session guard ใน composition; outgoing ไม่แจ้งเตือน, conflicting replay ไม่เรียก callback, notification failure ไม่ rollback Chat หรือขัดขวาง transport receipt. Native stable owner+message SHA-256 tag/cache (bounded 2,048 receipts/evict oldest 256) ช่วย dedup retries/restarts; in-app active state suppress alert. Notification permission เป็น optional, Android importance HIGH channel / iOS UNUserNotificationCenter alert+sound; generic body ไม่ส่ง Chat text/sender/coordinates ไป lock-screen payload. แตะแจ้งเตือนเปิดแอปตาม OS default ยังไม่ deep-link ไปเหตุ. ไม่มี APNs/FCM/backend push; ต้องได้รับ BLE message จริงจึงแจ้งเตือนได้. OS channel/Focus/user settings ควบคุม heads-up/sound. In-app notifications page เดิมยังเป็น mock แยกจาก system Chat notifications.
- Native receipt cache เป็น bounded dedup ไม่ใช่ exactly-once OS banner guarantee: crash ช่วง OS accepted ก่อน save receipt หรือ eviction ของเก่ามากอาจ alert ซ้ำ; permission denied/no Bluetooth delivery ไม่มี popup และไม่มี automatic historical notification backfill. GPS continuous background, media transfer และ signed final Chat receipt ไม่ได้เพิ่มในรอบนี้.

Host tests ไม่จำลอง OS scheduling/Doze/notification UI และ build ผ่านไม่ใช่ background device acceptance.
