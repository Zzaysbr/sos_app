# SOS route refresh

The SOS route panel shows the latest recorded authenticated evidence, not a live radio map. Contact freshness remains governed separately by `sos.presence.v1`.

When the same origin arrives through a different verified path, `RescueInboxRepository` updates incoming path/hop count without changing acceptance ID, accepted time, Chat, incident identity or history. Older leases and terminal/locally archived incidents cannot replace the path. Signatures, immutable digest and existing hop limits remain required.

An already accepted rescuer automatically queues signed feedback using the existing `rescue.offer` envelope and `sos-received-path-v1` binding. A deterministic `route:<SHA-256>` ID binds the origin/digest, responder, path and observation time, avoiding collision with the original Help Offer and duplicate reports for the same observation. This is a responder's signed report of its received SOS path, not an independent end-to-end measurement of radio range. A new path does not require the user to accept help again.

The runtime also reconciles accepted UI rows with newer verified durable relay envelopes after an update/restart. An older first relay copy cannot overwrite a later candidate arrival. Unavailable or invalid evidence is skipped; it is never replaced by an invented hop or an unsigned presence path.

The origin and intermediaries project the newest valid signed report per responder using signed creation time, so delayed older feedback cannot replace it. Intermediary projection requires owner-scoped verified feedback and a route containing the local key. Attempt prefixes already covered by that report are suppressed. Recipients project their updated incoming path. Original offers and Chat history remain stored; no database migration, cloud/rules change or new wire schema is needed.
