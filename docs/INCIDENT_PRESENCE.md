# SOS contact visibility

Build 20 adds `sos.presence.v1`. All test phones must be updated before physical acceptance; a sender running an older build cannot supply these pulses.

Rescue Nearby and Helping lists show active incidents only while there is fresh contact evidence from the SOS author. Loss of contact is a view condition, not cancellation, resolution, expiry or stop-following. SQLite incident, acceptance ID, Help Offer and Chat records remain intact. A fresh pulse restores the same accepted incident without another Offer Help. Received History remains available. An already-open Chat/map is not forcibly closed. Actual terminal/archived states stay hidden even if old contact evidence exists.

The author emits a signed pulse approximately every 10 seconds while its own SOS remains active. Its signed lifetime is 45 seconds; the existing 5-second scheduler expires visibility, so remote-source loss is normally reflected within about 45–50 seconds of the last valid pulse. A confirmed native disconnect invalidates that path immediately. Other still-current paths can retain visibility until their own evidence expires. A live B–C link alone does not keep A's incident visible after A–B is lost.

The Ed25519 body binds kind/version, random message ID, incident ID, author key/public key, created/expiry times, fixed maximum hops and scope. Public pulses follow the existing public SOS authorization, pass only over current Session Proof routes, and may be forwarded by opted-in relays up to the existing three-hop limit. Their path must begin with the author, contain no loops and end with the proof-verified immediate sender. Path metadata is not a signed end-to-end route attestation and is never used to claim an exact route in the UI. The message ID/body/time bindings, signature and previously trusted incident author are checked before recording contact. A middle node cannot sign as the author, extend the signed expiry, or substitute another incident. Repeated pulse IDs cannot extend the first local freshness deadline, including during the five-second future-clock tolerance.

Private Direct SOS uses a signed `direct` scope, unicast only to the existing selected incident recipient. Reception additionally requires the existing Direct SOS sender/device binding and current proof; it cannot fall back to trusting an arbitrary key. Direct pulses cannot be forwarded or relabeled public. No pulse contains GPS, Chat text or media, and none is written to cloud/Storage.

Contact is ephemeral and owner/coordinator scoped, bounded to 128 incident entries, 16 live paths per incident and 512 freshness/forward-dedup entries each. Entries expire; session stop clears contact. There is no DB migration or acceptance mutation. Restart requires fresh contact evidence but retains the stored acceptance. Timestamp validation requires reasonably aligned device clocks; stale or excessively future evidence fails closed. This feature does not promise background/force-quit survival, unlimited radio range or instantaneous detection by the OS.

Host evidence: the focused protocol/UI/transport/lifecycle/Chat security suites passed 164 tests, followed by six presence runtime cases (including one added clock-tolerance replay regression): 165 unique checks across these runs. Cases cover real fresh public SOS over two hops before an Offer Help, private Direct isolation, A–B loss while B–C stays live, preservation of acceptance/Chat, reconnect without another Offer Help, alternative routes, forged relay pulses, stale replay, and actual cancellation remaining hidden. One earlier concurrent run timed out in three cases; rerunning those files serially passed 56/56, then the final serial focused run passed 164/164. Android arm64 Profile and signed iOS Profile build 20 artifacts completed; iOS strict signature/standalone preflight passed after correcting stale generated build metadata. No physical range/background result is inferred from these checks, and build 20 has not been installed yet. Device acceptance status is tracked in PROJECT_CONTEXT.md.
